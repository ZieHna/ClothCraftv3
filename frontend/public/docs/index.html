How ClothCraft works

ClothCraft is a made-to-order apparel shop with a design editor, a staff and administrator workspace, and a Decision Support System (DSS) that turns the shop’s own orders and stock records into forecasts, restock suggestions, customer segments, alerts and a business-health view. This page explains how each part is built and how the numbers are produced, and it states what has and has not been verified.

Read this first: the data in the development shop is synthetic

The orders, customers, staff, restocks and stock counts in the development shop database (clothcraft_shop) were generated by the project’s scenario pack and replayed through the shop’s own API so that the DSS has a year of history to work on. They are not real sales and have not been independently verified. Every accuracy figure on this page therefore shows that the methods run correctly on that data. None of them is evidence of accuracy on real business outcomes. See section K and section L.

ASystem overview

What ClothCraft does

Customers browse garments (T-shirts, hoodies, long sleeves, onesies and similar), see prices and stock, and either buy a plain garment or design their own print in the in-browser editor, starting blank or from a premade design. Orders are paid by bank transfer or cash on delivery and move through a fulfilment lifecycle handled by staff. Behind the shop, the same database that holds orders and stock feeds the DSS, which reads it and writes its results back into dedicated tables.

Who uses it

Customers

Browse, customize, order, track and confirm receipt. Reached through the public storefront. An account is needed for the editor, the cart and orders.

Inventory Staff (employees)

Work orders, stock, restocks and suppliers at /staff. Security group “Inventory Staff”.

Administrators

Everything staff can do, plus approving restocks, managing employees and customers, the dashboard and the DSS at /admin. Security group “Administrator”.

The storefront API service

Not a person: the FastAPI service signs in to Odoo with its own restricted group (“Storefront API service”).

How the parts relate

  • Storefront and editor (React, in the browser) show products and let a customer build a design. They only ever call /api on their own origin.
  • The API service (FastAPI) checks the request and session, then calls Odoo’s JSON-2 interface. It is the only thing that talks to Odoo for the browser.
  • Odoo 19 with two custom modules holds the business rules: clothcraft (catalogue, orders, stock, restocks, suppliers, designs, audit) and clothcraft_dss (the DSS runner and result tables).
  • PostgreSQL 16 stores everything, including the DSS results. The DSS engine reads it with read-only SELECT statements.
  • The admin interface is part of the same React app, under /admin, and reads DSS results through /api/admin/dss/*.

What the DSS helps decide

  • How much to expect to sell in the next eight weeks, per garment, per garment type and in total (forecast with ranges).
  • What to reorder, from whom, how much and by when for each size and colour (restock suggestions). Nothing is ordered automatically.
  • Which customers are recent, frequent or lapsing (RFM segments).
  • What needs attention now: unpaid bank transfers, forecast stock-outs, low stock, restocks late or blocked by supplier availability.
  • How the business is trending: monthly revenue, spending, margin view, stock value and a short projection.

CHow the shop works

Customers

  • Browsing. The Category page lists products with filters (group, garment type, text, price range, in-stock only). Each card shows the shop’s own price (VAT included) and a stock badge: in_stock, low_stock or out_of_stock. Featured products come from GET /api/catalogue/featured.
  • Premade designs. The Featured section shows design mockups for five featured products; Browse all designs (/designs) lists twelve premade designs from a single catalog file (frontend/src/designs/catalog.ts) that holds no prices or stock. “Customize Design” opens /design?template=…: the editor loads a copy of the template as editable layers, fitted to the chosen garment’s print area. The shared template files are static and are never written to. Nine designs are fully editable; three contain one flattened picture layer that can be moved, resized and rotated but not redrawn.
  • Garment, colour, size. Chosen on the product page or inside the editor. Variants are real Odoo product variants with their own SKU.
  • Editor. Text, shapes and uploaded PNG/JPEG/WebP pictures as layers inside the garment’s print box, undo/redo, up to 50 elements per design (server limit). Signed-in customers get autosaved drafts in the browser for designs started from blank; a design started from a premade template is not autosaved as a draft (add it to the cart to keep it).
  • Print fee. A designed garment carries a per-piece fee computed from the area covered by the design (bounding boxes, overlaps counted once) times a rate, plus a size step. The browser shows an estimate; the server (addons/clothcraft/design_fee.py) is the authority. Both run against one shared file of test cases.
  • Cart and checkout. Signed-in customers have a server-side cart; the customer ticks the lines to buy and the server issues a quote (POST /api/cart/quote). Checkout offers bank transfer or cash on delivery. Placing the order runs a stock guard under a lock, so stock cannot be oversold.
  • Account and orders. The Account page lists the customer’s orders and saved drafts; each order has a tracking view. The customer can confirm that the order was received (POST /api/orders/{id}/received), which closes it; orders also close automatically after a configurable number of days (the shop setting auto-close days).

Employees and staff

Inventory Staff sign in through the employee door (/staff). They see the order board and order list and can move orders along the lifecycle; manage stock (view, history, record a stock edit); create and edit restock requests while a request is still requested; and maintain suppliers, their supply lines and unavailable dates. They cannot approve, reject or receive a restock. Odoo’s record rules, not the screens, enforce what each group may see and change.

Administrators

  • Dashboard and order summary (/admin, /admin/orders): counts and the full order list.
  • Stock and restocks: everything staff do, plus setting the low-stock levels (a global level and per-variant overrides), and approve, reject, receive or mark “not received” on restocks. Receiving creates a real stock receipt and records the actual cost (VAT included).
  • Suppliers and their price lines.
  • Employees (create, edit, change role, reset password, deactivate, reactivate) and customers (view, edit, deactivate, reactivate).
  • Forecast and DSS: /admin/dss (overview of the latest real and simulated runs, the run list and Run now) and /admin/dss/forecast (forecast chart, accuracy table, plain-language meaning and recommended actions).

Not implemented or not verified

  • Not yet implemented Dedicated admin screens for restock recommendations as a table, customer segments, alerts and business health. Their results are stored and served by the API (/api/admin/dss/restock, segments, alerts, health), but the frontend has no page that draws them yet.
  • Not yet implemented The header’s “Need help?” item is still marked Coming soon.
  • Unverified The customer journey from a premade design to a paid order has not been run end-to-end against the real shop with a signed-in customer (it was exercised on the mock shop and by unit tests). Registering a test customer would write to the shop database, so it was not done.

DApplication architecture and data flow

Three data paths matter. They are drawn together in Figure 3.

  1. Shop path. Browser → /api (Vite proxy in development) → FastAPI → Odoo’s clothcraft.api facade (one method per operation) → PostgreSQL. A confirmed order creates sale-order lines and reserves stock; staff actions write order history and stock moves; every lifecycle change is appended to clothcraft_order_audit.
  2. Design path. Premade templates are static JSON and PNG in frontend/public/designs/. The catalog file describes them; it is separate from product inventory. When a customer saves a designed line, the design (layers, preview, print image) is stored with clothcraft.design and the line carries its design id.
  3. DSS path. A run is triggered only by an Odoo scheduled job, never inside a web request: the weekly job (installed inactive) or the “Run now” job that the administrator’s button queues. The run reads native Odoo tables, computes in memory, and writes seven result tables in one transaction. The admin screens read those tables through /api/admin/dss/*.

FThe Decision Support System

Purpose, architecture and role

The DSS answers four questions for the administrator: what will we sell, what should we reorder, who are our customers, and what needs attention? It is a batch system. Once per run it reads the database, recomputes everything from scratch, and stores a complete, immutable set of results labelled with the rules and parameters used. It makes recommendations only: it places no orders, edits no stock and notifies nobody.

How a run is started and protected

  • Weekly job: Monday 03:00 Manila (Sunday 19:00 UTC), installed inactive; an Administrator switches it on.
  • Run now: a job that is active but parked at the year 2999; the button only adds a trigger, so a web request never computes anything.
  • One at a time: a transaction-level advisory lock; a second run logs and stops.
  • Interrupted runs (time limit or restart) are recorded as failed on the next start instead of being computed again silently.
  • Reproducibility: no clock or random source is used inside the methods; the run row stores parameters, library versions and a fingerprint of the input tables, so the same data gives the same output.

The DSS reads those records, rebuilds a week-by-week sales history and a day-by-day stock history, and applies fixed statistical and rule-based methods to them. It does not collect extra data, watch the web or learn from outside sources.

Three kinds of data that must not be confused

Normal application records

Whatever the running shop writes: real orders in a real deployment. A DSS run labels itself with the rules it applied.

Synthetic scenario data

The scenario pack: 370 invented orders from 112 invented customers (plus the shop’s own 2 orders), 8 invented employees, 31 restocks and 38 stock counts, covering 2025-10-01 to 2026-10-26. Recognisable by @example.test emails and the order reference pattern api:…:pack:O…. It is stored in clothcraft_shop.

Evaluation-only reference data

testdata/dss-scenarios/ground_truth.csv (357 rows) lists what the DSS should show, written in advance from the rules. It is used to check the DSS and is never an input to a run.

A labelling gap

The DSS screens badge a run REAL DATA when the database has no simulation marker. The development shop now holds the synthetic scenario history but has no such marker, so a run on it is badged REAL DATA although its orders are synthetic. The badge has not been changed; treat every number in the development shop as demonstration data.

Missing data, zero sales, stock movements and balances

  • Zero-sales weeks are real zeros: the weekly table is built on a full product-by-week grid and filled with 0, so the methods see quiet weeks.
  • Censored weeks. Demand lost while an item is out of stock is not recorded anywhere. A series-week is flagged censored when at least 25% of its variant-days ended with on-hand ≤ 0. Metrics are reported for all weeks and for uncensored weeks. The flag detects only end-of-day zero on-hand; shortages hidden by reservations, or a stock-out earlier in a day that ends positive after a same-day receipt, are not detected. Demand is therefore still understated for items that sell out.
  • No forecast is invented. A product that never sold in the training window gets no forecast row. A product with fewer than 8 weeks with a sale (thin) gets its garment type’s recent average times its own share, flagged not_enough_history, with an interval twice as wide.
  • Shortage of history. With fewer than 16 complete weeks with sales, the forecast is skipped and the run says so. Health labels its trend not_enough_history until 8 complete months exist.
  • Absent tables. Shop-only tables (suppliers, restocks, stock alerts, order audit) are optional: if missing, the extractor returns an empty frame and the alert kinds depending on them say not_available_on_this_data.
  • Inventory counts. A stock count that finds or removes units is an inventory-adjustment stock move; it enters the rebuilt balance like any other move.
  • Reservations are not stored historically by Odoo, so the reserved quantity per day is an approximation (an outgoing move holds its quantity from creation to completion); the DSS labels it so.

How a method is evaluated and chosen

  1. For each origin, every method forecasts the next 8 weeks of every product from the weeks before that origin only.
  2. Only product rows where all compared policies have a forecast are used, so policies are compared on the same weeks.
  3. The overall policy is the one with the lowest product-level WAPE among naive, ma4, ets, ets_croston. It is judged against the better baseline: if the best candidate does not beat it, the baseline is chosen and every forecast row is flagged baseline_wins.
  4. A single product gets its own method (an override) when another method beats the overall choice by more than 5 WAPE points on that product. Thin products are never overridden.
  5. The final forecast starts from the week after the last complete week, uses each product’s chosen method, and stores 8 rows per series with the method, flags and 80%/95% ranges.
  6. Variant shares split a product’s forecast across sizes and colours: units over the last 26 weeks, scaled up for days the variant was out of stock, with Laplace smoothing: share = (adjusted + 1) / (sum of adjusted + number of variants).

Metrics, as implemented

e = forecast − actual
MAE = mean(|e|)
WAPE = 100 × sum(|e|) / sum(actual)
bias = 100 × sum(e) / sum(actual)   (positive = over-forecast, negative = under-forecast)
coverage80 / coverage95 = % of scored weeks whose actual fell inside the 80% / 95% range
  • WAPE is the total size of the errors as a share of total sales. Lower is better; 0% is perfect. It weights busy weeks more than quiet ones, so a few units of error on a tiny series barely moves the total but dominates that series’ own score.
  • Bias says which way the forecast errs. A bias of −20% means that over the scored weeks the forecasts added up to about 20% less than what sold. Read it together with WAPE: a forecast can have near-zero bias and a large WAPE when over- and under-forecasts cancel out.
  • Coverage checks the ranges. An 80% range that contains the actual 80% of the time is calibrated; lower means ranges too narrow.
  • Only rows that have a forecast are scored, so a method that returns nothing (seasonal naive without a year of history) is not penalised or flattered with zeros; n is reported with every metric.

Limitations of the approach: weekly demand per product is small (a few units), so product-level percentages are noisy; the methods see no promotions, prices, holidays or marketing; lost demand during stock-outs is invisible; intervals assume the future errors look like the recent ones.

IRestock and inventory decision rules

Source: engine/restock.py. One row is produced per garment variant whose product has a forecast. The output is a recommendation; a person creates and approves the actual restock ticket.

From demand to a recommendation

  1. Demand per day = the product’s weekly forecast × the variant’s share, spread evenly over the week’s days. Only days after the as-of day count, so the current week contributes its remaining days. Past the last forecast week the last week’s rate is repeated (flag extended_beyond_horizon).
  2. Position = free stock (on hand − reserved, internal locations) + incoming (open incoming moves and lines of approved or not-received restocks).
  3. Run-out day = the first day whose cumulative demand exceeds the position; days_left is the days before it. A pessimistic run-out uses the upper 80% bound.
  4. Lead time L per supplier: the 90th percentile of its receipts if it has at least 3, else the supplier-info delay, else 10 days; rounded up to whole days.
  5. Safety stock SS = z × σ × √((L + R) / 7), with z for the service level, σ = the product’s backtest RMSE at 1–2 weeks ahead × the variant’s share.
  6. Reorder point = demand over L + SS. Order-up-to level S = demand over (L + R) + SS.
  7. Suggested quantity = ceil(max(0, S − free − incoming)), raised to the supplier’s minimum if any, and capped at 12 weeks of average forecast demand (flag capped).
  8. Order by = the day the position falls to the safety stock, minus L. If that is on or before the as-of day the status is order_now.
  9. Supplier choice (eligible suppliers only: active, switched on, not unavailable today or during the expected arrival, with a supply line for the variant’s garment type, size and colour): suppliers that arrive before the run-out day first, then lowest landed unit cost, then shortest L, then name. Alternatives are stored.

Historical stock balance and the opening-balance rule

The DSS rebuilds each variant’s end-of-day stock from its done stock moves. The stored stock dates are never changed. During integration of the scenario pack into the development shop, the original operational stock dates were preserved: the shop’s 243 opening-stock moves keep their original date (2026-10-23), and the “D1” step that would have re-dated them was deliberately not run on the shop.

Because that opening stock is dated after the first sales, a plain rebuild would show many variants below zero, hence “out of stock”, until the opening date. The engine therefore applies an opening-balance rule (transform.backdate_opening) in memory only, for the reconstruction:

  • A variant’s opening move is its first-entered (lowest id) done inbound move, if that is an inventory adjustment of positive quantity.
  • The rule applies only when, without that move, the running balance goes below zero on some day before the move’s own day, counting real receipts and outgoing moves as cover (stock added by a later count is not treated as cover).
  • It then counts that one move from the earlier of the variant’s first other move and the start of history. Only its day moves; its quantity is counted once; no other move changes; nothing is written anywhere.
  • It does not apply when the opening stock is dated early enough, when there is no opening move, or when the balance never goes negative.

Assumption: a lower move id means it was entered earlier. The reconstruction is only as good as that assumption. Covered by tests in engine/tests/test_transform.py.

Business health

Source: engine/health.py. All money is VAT included. Revenue counts only Closed orders.

  • Monthly series (whole Manila months; the as-of month is partial and flagged): earned revenue; spending (received restocks by month received, plus purchase-order receipts at line cost); cost of goods sold (garment units of revenue orders × the variant’s last purchase cost, in the month of their revenue); cash view = revenue − spending; margin view = revenue − cost of goods sold. The supplier opening balance is a starting investment: never spending, never a loss.
  • Projection: revenue for the as-of month’s remaining days and the next months, from the total forecast × revenue per unit (Closed revenue of the last 3 complete months / garment units). NGlossary and references

Business Intelligence (BI)
Collecting, organising and analysing business data so people can make better decisions.
Decision Support System (DSS)
Software that analyses data and presents options or recommendations for a person to decide on. ClothCraft’s DSS is batch-computed and recommendation-only.
ETL
Extract, Transform, Load: reading data from source systems, cleaning and reshaping it, and storing the result for analysis.
KPI
Key Performance Indicator: a number that tracks a goal, such as WAPE for forecast quality or stock cover for inventory.
WAPE
Weighted Absolute Percentage Error: 100 × (sum of absolute errors) / (sum of actual values).
Forecast bias
100 × (sum of signed errors) / (sum of actuals). Negative means the forecast is too low on balance.
Backtesting
Judging a method by pretending to forecast from past points in time and comparing with what then happened.
Rolling origin
A backtest that repeats the forecast from several successive origin dates, each time using only earlier data.
Prediction interval (range)
A band expected to contain the actual value a stated share of the time (80% or 95% here).
Censored demand
Sales that could not happen because stock ran out, so recorded sales understate true demand.
Intermittent demand
Demand with many zero periods, forecast here with Croston’s method.
RFM
Recency (days since last order), Frequency (number of orders) and Monetary value (total spent): three measures used to group customers.
Lead time
Days from approving a purchase or restock to receiving the goods.
Safety stock
Extra stock held to absorb forecast error during the lead time plus review period.
Reorder point / order-up-to level
The position at which to reorder / the target position an order should lift stock to.
Inventory balance
Units on hand at a point in time; here rebuilt from stock movements for each end of day.
Restock recommendation
The DSS’s suggested quantity, supplier and order-by day for a variant. A suggestion, not an order.
Closed order
An order that finished its lifecycle (the customer confirmed receipt, or it closed automatically). Only Closed orders count as revenue and in RFM.
Append-only
Rows can be added but never edited or deleted, enforced by database triggers for DSS results.

D. Configure environment variables

ClothCraft keeps its settings in .env files that are never uploaded to GitHub (they are in .gitignore). You create them from the examples. There are three places, and only the first two need you to do anything.

1. .env in the project folder: the database login

Copy-Item .env.example .env
notepad .env

The file has two settings. Both are yours to choose; nothing in the project needs particular values:

POSTGRES_USER
Use odoo. The commands in this tutorial use -U odoo; if you pick another name, replace it in those commands.
POSTGRES_PASSWORD
A long random password of your own, used by both the database and Odoo containers. To generate one in PowerShell: -join ((48..57)+(97..122) | Get-Random -Count 24 | ForEach-Object {[char]$_}). Paste the result after the equals sign, with no spaces and no quotes. Do not reuse a real password.

Now tell Docker Compose to use the development files together. Add these two lines at the end of the same .env (they just save you typing two -f options on every command):

COMPOSE_PATH_SEPARATOR=;
COMPOSE_FILE=docker-compose.yml;docker-compose.dev.yml

Save and close the file. Important: PostgreSQL only reads POSTGRES_PASSWORD the first time it creates its data. If you change the password later, the existing database keeps the old one (see part J).

2. backend/.env: the API service

Copy-Item backend\.env.example backend\.env

Leave it as it is for now. What is in it:

  • ODOO_API_KEY and SESSION_SECRET: you do not type these. A setup script in part F creates a new key and a random secret and writes them here. SESSION_SECRET signs customers’ login cookies and the service refuses to start without it. If you ever change it, everyone is signed out.
  • DELIVERY_LABEL, BANK_NAME, BANK_ACCOUNT_NAME, BANK_ACCOUNT_NUMBER: development defaults and clearly marked placeholders (“Sample Bank (placeholder)”). Leave them. The shop then tells customers “Do not send money” for bank transfers.
  • The Odoo address, the database name and the allowed browser origin are set by docker-compose.dev.yml, not here. The optional lines that start with # can stay commented.
  • The staff test accounts: the script in part F also writes two test logins (their emails and random passwords) at the bottom of this file. They exist only in your copy. Never paste this file into a chat, an email or an issue.

3. frontend/: how the storefront reaches the API

Nothing to create. The committed frontend/.env.development says VITE_API=odoo and VITE_PROXY_TARGET=http://127.0.0.1:8000. The browser only ever calls /api on its own address (http://localhost:5173); the Vite dev server forwards those calls to the API service on port 8000, which calls Odoo, which talks to PostgreSQL. To override a value for yourself, create frontend/.env.local (also ignored by git).

Files that must stay on your computer and never be committed

  • .env and backend/.env (passwords, API key, session secret)
  • backups/ and any *.dump (they contain customers and password hashes)
  • testdata/dss-scenarios/_local/ (sign-in accounts for the optional demo)
  • scripts/mcp_dev/.env

All of these are already listed in .gitignore. Run git status before any commit and look at every file it lists.

E. Build and start the system with Docker

Which setup? Use the development stack: docker-compose.yml (PostgreSQL and Odoo) plus docker-compose.dev.yml (adds the API service and makes Odoo serve only the clothcraft_shop database). That pair is what you selected with the COMPOSE_FILE line in part D. The third file, docker-compose.dss-bundles.yml, is only for importing a simulated DSS bundle on a demo database; ignore it.

From the project folder:

docker compose build odoo api

build makes the two images that are not downloaded ready-made: the Odoo image (the official Odoo 19 image plus the Python libraries the DSS needs: pandas, numpy, statsmodels) and the API image. The first time it downloads a lot and can take several minutes. Then start only the database:

docker compose up -d db
docker compose ps

-d means “detached”: the container runs in the background and you get your prompt back. docker compose ps lists the containers; the db line should say Up. The project defines no health checks, so “Up” plus a successful check in part H is how you know a service is ready. Wait about 10 seconds before the next part, until:

docker compose exec -T db sh -c 'pg_isready -U "$POSTGRES_USER"'

prints accepting connections.

Why not start everything now? The API service cannot start until it has an API key, and the key can only be made after the database exists (part F). You start Odoo and the API at the end of part F.

Useful at any time:

docker compose logs --tail 50 db       # the last 50 log lines of one service
docker compose logs -f odoo            # follow a service live (Ctrl+C stops following, not the service)

F. Database and Odoo initialization (first run only)

ClothCraft does not create its database or install its modules by itself. You do it once, in this order. The order matters: the shop’s chart of accounts and 12% VAT come from the company’s country at the moment the accounting module is installed, so the company must be set to the Philippines before ClothCraft is installed.

Why some commands use cmd /c

Several steps feed a script file to Odoo’s shell. In Windows PowerShell 5.1, piping a file (Get-Content file | docker ...) silently adds an invisible byte-order mark, and Odoo stops with invalid non-printable character U+FEFF. This happened during testing. cmd /c “... < file” sends the file byte for byte and works. (Some older examples in README.md use the pipe form.)

Step 1 – create an empty database named clothcraft_shop (the name the development stack is set to serve):

docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" -E UTF8 -T template0 clothcraft_shop'

Step 2 – install Odoo’s base module (about 20 seconds in the test):

docker compose run --rm --no-deps odoo odoo -d clothcraft_shop -i base --stop-after-init --without-demo=True

run --rm starts a one-off Odoo container that is deleted when it finishes; --no-deps does not start other services; -i base installs a module; --stop-after-init exits when done; --without-demo=True leaves out Odoo’s sample data.

Step 3 – set the company to the Philippines and PHP:

cmd /c "docker compose run --rm --no-deps -T odoo odoo shell -d clothcraft_shop --no-http < config\set_ph_company.py"

The last line printed should be Company set to PH PHP. If it is not, stop and fix this before going on. (Installing ClothCraft with the wrong company cannot be undone cleanly; the way out is to drop the empty database and start again at step 1.)

Step 4 – install the ClothCraft module and the DSS module (about 95 seconds and 10 seconds in the test):

docker compose run --rm --no-deps odoo odoo -d clothcraft_shop -i clothcraft --stop-after-init --without-demo=True
docker compose run --rm --no-deps odoo odoo -d clothcraft_shop -i clothcraft_dss --stop-after-init --without-demo=True

Step 5 – load the shop catalogue: the 19 garments, their 246 colour-and-size variants, pictures, prices and a starting stock. There are no customers, orders or simulated history.

cmd /c "docker compose run --rm --no-deps -T -v ""%CD%\assets-v1:/mnt/assets-v1:ro"" odoo odoo shell -d clothcraft_shop --no-http < scripts\seed_catalogue.py"

Success ends with a line that starts SHOP CATALOGUE SEEDED clothcraft_shop | garments 19 | variants 246. The script refuses to run on any other database or one that already has garments, so running it twice is safe.

Step 6 – create the API service user, then the staff test users. Run them in this order. Each writes into backend\.env and never prints a secret:

cmd /c "docker compose run --rm --no-deps -T -v ""%CD%\backend:/out"" -e API_KEY_OUT=/out/.env odoo odoo shell -d clothcraft_shop --no-http < scripts\create_api_user.py"
cmd /c "docker compose run --rm --no-deps -T -v ""%CD%\backend:/out"" -e STAFF_OUT=/out/.env odoo odoo shell -d clothcraft_shop --no-http < scripts\create_staff_users.py"

Expect API USER READY api_shop ... and STAFF USERS READY. To confirm the file was filled without showing the secrets, run this (it prints names only):

Get-Content backend\.env | Where-Object { $_ -match '^[A-Z_]+=' } | ForEach-Object { ($_ -split '=')[0] + '=' + $(if (($_ -split '=',2)[1]) {'<set>'} else {'<empty>'}) }

Every name, including ODOO_API_KEY, SESSION_SECRET and the four STAFF_… lines, should say <set>.

Step 7 – start Odoo and the API and wait a few seconds:

docker compose up -d odoo api
docker compose ps

All three services (db, odoo, api) should say Up. Now go to part G.

What the different database operations mean

Create a fresh database
Step 1: an empty PostgreSQL database. Nothing in it yet.
Install a module
-i name: Odoo creates the module’s tables and loads its starting data. Done once per database.
Upgrade a module
-u name: after you pull new code, Odoo applies the module’s changes (new columns, migrations) to an existing database. Take a backup first (part I) and see part L.
Restore a backup
Puts the contents of a .dump file into a database. It also needs the pictures (the filestore) to be restored separately, or product pictures will be missing. The project’s tested restore is scripts\pack_run.ps1 restore in testdata\dss-scenarios\RUNBOOK.md. Not tested as part of this tutorial.
Load optional demo data
The DSS scenario pack adds a year of invented orders. See below: it goes in a separate database, never in clothcraft_shop.

Optional: demo data for the DSS (synthetic)

A fresh shop has no sales, so the forecast has nothing to work on (it needs at least 16 weeks with sales). To see the DSS working, the project has a scenario pack: 370 invented orders from 112 invented customers, 2025-10-01 to 2026-10-26. It is synthetic, for demonstration and evaluation only; it is not independently verified sales history. Follow testdata\dss-scenarios\RUNBOOK.md. It loads into its own database, clothcraft_pack_20261026, using scripts\pack_run.ps1, and needs two files from the project owner (a database dump and a product-pictures archive) that are deliberately not in git. Do not load it into clothcraft_shop by default. The loader refuses the shop database unless an explicit backup variable is set, and the date-rebasing step (“D1”) must never be run: the shop’s original stock dates are kept. Not tested here (it was run and checked earlier in the project).

Danger zone: destructive commands (not part of normal setup)

docker compose down -v deletes the containers and the database and file volumes: every database, order, customer and picture is gone. dropdb deletes one database. Never use them to “try fixing” a problem. Use them only on a copy you can afford to lose, after a verified backup (part I) and after reading README.md. Nothing else in this tutorial deletes data.

K. Handover notes and system architecture

How the parts fit, in plain words

A visitor’s browser shows the storefront (the React app in frontend/). It never talks to the database. It sends every request to /api on its own address. In development the Vite server passes those to the API service (FastAPI, backend/), which checks the request and the login cookie and then asks Odoo to do the real work. Odoo holds the business rules (our clothcraft addon) and stores everything in PostgreSQL. The DSS (the clothcraft_dss addon and its engine) is a batch job inside Odoo: it reads the shop’s own orders and stock tables, works out forecasts and suggestions, and stores the results in its own tables, which the admin screens read through the API. Section D of this page has the drawings.

L. Update and maintenance

The repository has one branch, main, and no other branch convention is written down in it. If you want to change code, make your own branch first (git switch -c my-change) so you never edit main directly.

Pulling new changes safely

git status                         # is anything of yours uncommitted? commit it on your branch first
git fetch                          # look at what is new; this changes none of your files
git log HEAD..origin/main --oneline   # the commits you are about to receive
git switch main
git pull --ff-only                 # takes the new commits only if it can do so without overwriting anything

If git pull --ff-only refuses, stop: it means your main and the shared one have diverged. Do not run git reset --hard or git clean to make the message go away; ask the person who maintains the repository, or move your work to a branch first. Your .env files are ignored by git, so a pull never touches them.

Then rebuild only what changed

  • frontend/package-lock.json changed → in frontend: npm ci.
  • Dockerfile or backend/requirements* or backend/app changed → docker compose build odoo api, then docker compose up -d.
  • Files in addons/ changed (look for a new version in an addon’s __manifest__.py) → make a backup first (part I), then stop Odoo and upgrade, then start it again: 
    docker compose stop odoo
docker compose run --rm --no-deps odoo odoo -d clothcraft_shop -u clothcraft,clothcraft_dss --stop-after-init
docker compose up -d odoo
    Success ends with a line like Registry loaded in ...s and no ERROR lines. (The upgrade command was tested for the DSS module; stopping Odoo first is what README.md recommends.)
  • frontend/vite.config.ts changed → restart the dev server.

Your database, backups and .env files stay as they are through all of this.

Reporting a bug

Send: what you did, step by step; what you expected; what happened instead; the output of git rev-parse --short HEAD; your operating system, docker --version and node --version; and the last 20 to 50 lines of the one relevant log (docker compose logs --tail 50 api), after reading them. Do not send: .env or backend\.env (or a screenshot of them), passwords, the API key, cookies, database dumps or backups, customer names, emails or addresses, or whole log files. Replace anything personal in a log line with <removed>.
